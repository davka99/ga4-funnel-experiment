# Decision log

| Date | Decision | Reason | Alternative considered |
|------|----------|--------|------------------------|
| 2026-11-10 | Funnel steps are `session_start` → `view_item` → `add_to_cart` → `begin_checkout` → `add_payment_info` → `purchase`. | `add_shipping_info` has almost exactly the same users as `begin_checkout` (9,714 vs 9,715), so it adds no information. | Keep `add_shipping_info` as a separate step between `begin_checkout` and `add_payment_info`. |
| 2026-11-10 | Exclude `view_item_list` and `select_item`. | The tracking is inconsistent (71 vs 31,007 events). | Include them as list-browsing steps before `view_item`. |
| 2026-11-10 | The primary experiment KPI is checkout conversion = users who purchase / users who begin checkout. | It matches the business question. The rough baseline is about 45.5% (not yet order-checked). | |
| 2026-11-10 | `stg_ga4__events` keeps every raw event row (no deduplication) and defines `session_key = user_pseudo_id-ga_session_id`. | Staging should mirror the source at event grain. Duplicates are measured first and handled downstream if needed. | Deduplicate in staging on (user_pseudo_id, event_ts, event_name). |
| 2026-11-10 | Warn (not fail) when more than 1% of `stg_ga4__events` rows have a NULL `session_key`. | Events without `ga_session_id` cannot be assigned to a session. 1% is an initial assumption to revisit once the actual share is known. | Fail on any NULL `session_key`. |
| 2026-11-10 | Enforce uniqueness of (`user_pseudo_id`, `event_ts`, `event_name`) in `stg_ga4__events` with an error-severity test. | The control query (`02_stg_events_checks.sql`) found 0 duplicates in 4,295,584 rows. Downstream session and funnel counts assume this keeps holding. | Warn-level test, or deduplicate in staging. |
| 2026-11-10 | Materialize `stg_ga4__events` as a table instead of a view. | As a view, each test re-scanned the raw export (dry run: 1.37 GiB for a single `not_null` test). As a table, the raw data is scanned once per build (1.7 GiB) and the six tests scan 33–171 MiB each (about 0.49 GiB in total). Sandbox tables in `funnel_dev` expire after 60 days, and the table is rebuilt by `dbt build`. | Keep the view and accept about 1.4 GiB per test. |
| 2026-11-10 | Cluster `stg_ga4__events` by (`event_name`, `event_date`), with no partitioning. | Downstream models filter on event names, which clustering prunes well: the purchase check estimated 61 MiB but processed 9.7 MB. Three months of data (835 MiB) is too small to benefit from partitioning. | Partition by `event_date` and cluster by `event_name`. |
| 2026-11-10 | `int_ga4__session_funnel` has one row per `session_key`. Rows with a NULL `session_key` are excluded (currently 0). `session_start_date` is the session's earliest `event_date`. | Session grain is needed for step flags. `event_date` is the export date used everywhere else, and taking the minimum handles sessions that cross midnight. | Use the date of the `session_start` event, or the UTC date of the first `event_ts`. |
| 2026-11-10 | A funnel step is reached only if all earlier steps were reached and each step's first timestamp is >= the previous step's first timestamp. Ties count as ordered. | It enforces the step order using one timestamp per step, which keeps the flags explainable from the `first_<step>_ts` columns. 657 `begin_checkout` sessions and 27 `add_to_cart` sessions fail only on ordering (`04_session_funnel_steps.sql` plus an ad-hoc split). | Use the first occurrence of each step after the previous step was reached. This would keep sessions that repeat an earlier step later. |
| 2026-11-10 | The session funnel only counts steps within a single session. | It matches the session grain. Limitation: 5,156 of 11,106 sessions with `begin_checkout` have no ordered `add_to_cart` in the same session, so journeys that span sessions are not counted. | A user-level funnel across sessions (as in the primary checkout KPI). |
| 2026-11-10 | The purchase step uses the presence of a `purchase` event and does not require a valid `transaction_id`. | Of 5,692 purchase events, 23 have a NULL and 883 a `'(not set)'` transaction_id, and 326 IDs repeat across 661 events (`03_purchase_checks.sql`). Requiring a valid ID would drop about 16% of purchase events. | Require a non-NULL, non-`'(not set)'` transaction_id, or deduplicate by transaction_id. |
| 2026-11-10 | The primary KPI `checkout_conversion_7d` is measured per user, not per session. | 5,156 sessions with `begin_checkout` have no `add_to_cart` in the same session (`int_ga4__session_funnel`), so journeys span sessions. An experiment would also randomize per user, so the KPI must use the same unit. | Session-level conversion `begin_checkout` → `purchase` from `int_ga4__session_funnel`. |
| 2026-11-10 | `checkout_conversion_7d` is anchored on each user's first `begin_checkout`, with a 7-day outcome window. Users are included only if the window fits in the data (first checkout before 2021-01-25 UTC). | A fixed window gives every user the same time to convert. The anchor also matches the point where an experiment would expose users to a new checkout. | Count any purchase in the data range (unequal follow-up), or anchor on the last checkout. |
| 2026-11-10 | `n_sessions_before_checkout` counts observed sessions that started before the session of the first `begin_checkout`. | It uses only sessions visible in the data, so the count is consistent across users. History before 2020-11-01 is not visible. | `ga_session_number - 1` of the checkout session (GA's own counter, which includes earlier history). |
| 2026-11-10 | All date cut-offs for `int_ga4__user_checkout` are applied to UTC `event_ts`. | `event_ts` is the only precise timestamp. The export's `event_date` is in the property time zone. | Apply cut-offs to `event_date`. |
| 2026-11-10 | Test design for `checkout_conversion_7d`: 6 weeks, p0 = 0.4383, alpha 0.05 two-sided, power 0.80, giving an MDE of 4.13 pp (9.4% relative). Source: `analysis/power/power_mde.py`. | Traffic is about 760 users per week, and the baseline varies between 29% and 60% over the period. | 4 weeks (MDE 5.07 pp, 11.6% relative) or 8 weeks (MDE 3.58 pp, 8.2% relative). |
| 2026-11-10 | The experiment's primary metric is named `exp_checkout_conversion_7d` and is kept separate from the descriptive `checkout_conversion_7d`. | The two use different anchors and populations. `exp_checkout_conversion_7d` anchors on the first `begin_checkout` inside the experiment window 2020-11-16 to 2020-12-27 (5,962 users, p0 = 46.31%). `checkout_conversion_7d` anchors on the first `begin_checkout` since 2020-11-01, with first checkout before 2021-01-25 (9,232 users, 43.83%). One name for both would mix up the baseline and the experiment population. | One metric name with the population stated separately (used in experiment plan v1.0). |
| 2026-11-10 | `int_exp__enrolled_users.pre_sessions_14d` counts distinct sessions with any event in [trigger − 14 days, trigger), as defined in plan v1.2 §7.3. This includes the trigger session when it has events before the trigger. | It follows the registered definition literally, and every counted event happens before exposure. Result: no user has 0 (4,115 have 1, 861 have 2, 986 have 3+), ρ with `purchased_7d` = 0.2093, ρ² = 0.0438 (`07_exp_population_checks.sql`). | Exclude the trigger session (this would need a plan amendment). |
| 2026-11-10 | In `int_exp__enrolled_users`, `purchased_7d` counts any purchase event, while `revenue_7d` and `n_orders_7d` use only valid `transaction_id` (not NULL or `'(not set)'`), one row per ID, keeping the highest revenue for duplicated IDs. | The primary metric counts purchases (plan §4). The AOV guardrail requires valid, deduplicated orders. 114 of 2,761 buyers have no valid order. | Require a valid order for `purchased_7d`, or sum revenue over all purchase events. |
| 2026-11-10 | SYNTHETIC: assignment and all simulated draws in `synthetic_exp__*` use `FARM_FINGERPRINT` with fixed salts (`checkout-v1:`, `s1-effect:`, `s1-rev:`, `s2-drop:`) instead of a random-number seed. | It is deterministic and rebuildable with `dbt build` in BigQuery, and fills the same role as the "fixed random seed" in plan §6. | A seeded random-number generator in Python, writing tables back (not possible in the Sandbox without DML). |
| 2026-11-10 | SYNTHETIC: the revenue of a simulated purchase is drawn from the pool of real valid orders in the enrolled users' 7-day windows. Pool: one row per user and `transaction_id`, 3,094 rows, as in `int_exp__enrolled_users`, numbered by (`user_pseudo_id`, `transaction_id`). | It matches the order definition behind `revenue_7d`, so the simulated AOV effect is zero by construction (plan §6). 7 IDs appear for two users and 15 IDs have differing revenue across duplicate rows (`08_transaction_checks.sql`). | Pool of all valid orders in the data range, or control-group orders only. |
| 2026-11-10 | SYNTHETIC: simulated purchases have no timestamp column. The outcome is only the flag `purchased_7d` within the 7-day window. | Plan §6 says purchases are "timed within their outcome window". No planned analysis uses the purchase time, so a timestamp would not change any result. | Draw a timestamp uniformly in [trigger, trigger + 7 days). |
| 2026-11-10 | The AOV guardrail bootstrap resamples users within each group (cluster bootstrap), not orders. Logged before `analyze_experiment.py` was run. | Orders from the same user are not independent, so resampling orders would understate the variance of AOV. | Resample orders (plan v1.2 §7.4 says "resamples of orders"). |
| 2026-11-10 | Prediction, logged before any scenario was run: the SRM check (chi-square against 50/50, p < 0.001) with about 2,980 users per arm only detects drops of about 8–9% of one arm or more. The expected split reaches p = 0.001 at a drop of 8.3%, and a 3% drop gives an expected p of about 0.25. S2 (3% of treatment dropped) is therefore expected to pass the SRM check. | It records in advance that the registered threshold cannot catch S2, so a pass in S2 is not read as evidence of a correct assignment. The S2 group sizes (2,977 / 2,885) were already shown when the tables were built. No test result had been computed. | A looser SRM threshold (e.g. p < 0.01). |
| 2026-11-10 | `traffic_medium` and `traffic_source` come from the `traffic_source` record. | It is the only traffic attribution in the export. It describes the user's first acquisition, not the session's source. | Session-level source from event params (`source`/`medium`). These are not used yet. |
